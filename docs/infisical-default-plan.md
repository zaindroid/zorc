# Plan: make Infisical the default secret path across zorc

Status: **design only, nothing implemented, needs sign-off** (written
2026-10-12). Follows `docs/infisical-plan.md`, which shipped Redis,
the Infisical deployment, and opt-in `from_infisical` references. This
document scopes the next layer, which changes how every future deploy
handles secrets and, in part 3, touches the platform's own live
credentials. Nothing here should be built before the decisions in the last
section are answered.

## What is being asked

1. Recommend `from_infisical` over raw `env_overrides` values for any
   `required: true` env var; raw values become the escape hatch.
2. Auto-reuse: when a required var has no explicit value, look it up in
   Infisical under the calling owner's own project and use it, so a
   credential typed once is reused by every app that declares that name.
3. Migrate zorc's own credentials (`deploy/secrets/*`) into Infisical.
4. Document `deploy/secrets/infisical.json` as the deliberate exception
   and root of trust.

## Findings that shape the design

- **The platform has a dependency cycle.** Infisical is deployed and
  restarted *by zorc through Coolify*, with a Postgres and Redis that
  Coolify runs. So any credential needed to bring Infisical back up cannot
  live only inside Infisical. That makes the root of trust larger than the
  single file in point 4 (see part 3).
- **Resolution is at deploy/set time, not runtime.** Values are copied into
  the app's Coolify env when `deploy()`/`set_app_env_vars()` runs. Running
  apps do not depend on Infisical being up. Only *new deploys and
  updates that use references* do. This bounds the blast radius of an
  Infisical outage, and is the main reason raw `env_overrides` must stay as
  a working escape hatch.
- **Rotation is not actually "in one place" yet.** Changing a secret in
  Infisical does nothing to an already-deployed app until something
  re-resolves it. zorc does not currently record which app uses which
  reference, so it cannot do that. Without this, "default path" would
  promise rotation it cannot deliver.
- **Infisical's own keys are a single point of loss.** `ENCRYPTION_KEY` and
  `AUTH_SECRET` were generated by zorc and live only in Coolify's env;
  Infisical's data lives in a dedicated Postgres. Losing either makes every
  secret unrecoverable. `backup/backup.sh` covers Coolify's key; it does not
  yet cover Infisical's database or those two values. This must be solved
  *before* more depends on Infisical.

## Part 1: recommend references by default

Documentation and surfaced guidance only; no behaviour change.

- `get_platform_contract()` gets an `env_vars_beyond_defaults` rewrite and a
  new `secrets` entry: prefer `{"from_infisical": ...}`; literal values are a
  fallback for one-off or externally-owned values.
- `AGENTS.md` section 5 gets the same, plus the reference format and the
  `project_access` note.
- `analyze_deployment_requirements()` report: for each
  `required_from_caller` key, add a `suggested_reference` hint when an
  owner default project is configured (see part 2). Report only; it never
  fetches a value.

## Part 2: auto-reuse

### Resolution rule

For a `required: true` var `NAME` with **no** entry in `env_overrides`,
`resolve_env_vars()` looks, in order, at:

1. `<app-name>`-scoped: folder `/apps/<app-name>`, secret `NAME`
2. owner-wide: folder `/shared`, secret `NAME`

in the caller's **designated default project** and environment (`prod`
unless the owner's config says otherwise). First hit wins. No hit means the
var is reported missing exactly as today, with a message naming both
locations that were checked.

Hard rules:

- An explicit `env_overrides` entry always wins; auto-reuse never overrides
  what the caller supplied.
- `generate:` vars are never auto-reused.
- Only exact, case-sensitive name matches. No fuzzy matching.
- Never reads another owner's project. The project searched is derived
  from the **caller's identity**, never from the app name or repo.
- Only the two folders above. A secret elsewhere in the project is not
  auto-reusable, which makes reuse an explicit act ("I put it in /shared")
  rather than a side effect of what happens to exist.

### Why a designated project and a `/shared` folder

`project_access` today answers "may this owner reference project P", and
several owners can share one project. Auto-reuse is implicit, so it needs a
stricter question: "which single project is *this owner's* namespace".

New config key in `deploy/secrets/infisical.json`:

```json
"owner_defaults": {"<owner-name>": {"project_id": "<uuid>", "environment": "prod"}}
```

Validated at load: a project may be the default for **at most one**
non-admin owner. Two owners that both declare `GEMINI_API_KEY` each resolve
inside their own project, so they cannot collide or read each other's.

### The untrusted-repo problem

`app.yaml` is written by whoever authored the repo. Deploying a third-party
repo that declares `required: true` for `STRIPE_KEY` would otherwise
quietly receive the owner's real key. Mitigations, all required:

- Auto-reuse only reads `/apps/<app-name>` and `/shared`, i.e. things the
  owner deliberately placed there.
- `analyze_deployment_requirements()` lists exactly which keys would be
  auto-resolved and from which path (names and paths, never values), and
  `deploy()` rejects a report where that list changed after analysis.
- Open question for the user: should `/shared` reuse require a per-name
  allowlist on the app (`app.yaml` is not trusted for this, so it would
  live in zorc config or the report approval)? Default proposal: no
  allowlist, rely on the visibility above, since the owner reviews the
  report.

### Failure behaviour

- Infisical unreachable or the identity rejected: `deploy()` fails at the
  `resolve_env_vars` step before anything is created (same as today's
  explicit references). It does **not** silently fall back, since that would
  hide an outage as "missing secret".
- The caller can always pass the value through `env_overrides` to proceed.

## Part 2b (prerequisite): record references so rotation works

- Record `{KEY: reference}` per app in `resource_map.json` (reference path
  only, never the value).
- New owner-or-admin tool `refresh_app_secrets(name)`: re-resolves the
  recorded references, sets the changed env vars, redeploys. This is what
  makes "rotate in one place" true, and is the natural unit for later
  scheduled rotation.
- Auto-resolved keys are recorded the same way, so they rotate too.

## Part 3: zorc's own credentials

Inventory of `deploy/secrets/` (names only):

| File | What it is | Candidate? |
|---|---|---|
| `cloudflare.json`, `cloudflare_account.json` | Cloudflare API tokens | **Yes** |
| `iht_news.json` | appears app-specific (by name; contents not inspected) | **Probably** (belongs with that app, not the platform; confirm what it is first) |
| `coolify.json` | Coolify API token | **No, keep file** |
| `*_deploy_key` (5 SSH private keys) | node access | **No, keep files** |
| `infisical.json` | machine identity | **No, root of trust** |
| `mcp_token.json` (+ `.pre-migration.bak`) | hashed client bearer tokens | **No** (not a secret store use case; hashed) |

Reasoning for the exclusions:

- **Coolify token and SSH keys** are what zorc uses to deploy, redeploy
  and repair Infisical itself. Storing them only in Infisical means a
  broken Infisical cannot be repaired by the tool that would repair it.
  They are the break-glass tier and stay as files.
- **SSH keys additionally need to exist as files** for `ssh -i`; serving
  them from Infisical would mean writing them to disk on demand, which is
  strictly more exposure than the file at rest.
- **Hashed bearer tokens** are verification material, not recoverable
  secrets.

So realistically the migration is: Cloudflare tokens (and any app-level
credential such as `iht_news.json`), not "everything in the directory".

### Cutover design (side by side, no flag day)

1. **Accessor layer, no behaviour change.** One
   `get_platform_secret(name)` in `agent.py` that today reads the file.
   Call sites (`_coolify_headers`, `_cloudflare_headers`, ...) switch to it.
   Source selected per secret by config: `file` (default), `infisical`.
2. **Mirror.** A human puts the Cloudflare token into a dedicated
   Infisical project (`zorc-platform`) by hand. Agents never copy or
   read credential values to do this (conventions doc).
3. **Shadow read.** With source still `file`, zorc also fetches the
   Infisical copy on startup and logs **match / mismatch / unreachable**
   per secret (comparison by hash; no value in logs). A week of "match"
   is the gate.
4. **Cutover per secret**, only on explicit user approval, with the file
   retained and used as automatic fallback if Infisical read fails.
5. **File removal** only after a further agreed soak, and never for the
   break-glass tier.

Rollback at every step is "flip the source back to `file`".

## Part 4: root of trust note

Added to `docs/agent-session-conventions.md` after #16 lands (to avoid an
edit conflict in the same file): `infisical.json` is the one deliberate
exception, along with the break-glass tier above (Coolify token, SSH keys).
These are the things that must be placed by a human, backed up out of
band, and rotated by hand. Everything else can be a reference.

## Phasing

| Phase | Content | Risk |
|---|---|---|
| P0 | Prerequisites: back up Infisical's Postgres and key escrow, restore drill, pin the image version, rotate the client secret, set `owner_defaults` | none to platform |
| P1 | Part 1: contract/AGENTS.md/report hints | none (docs + report) |
| P2 | Part 2b: record references, `refresh_app_secrets` | low (new tool) |
| P3 | Part 2: auto-reuse | medium (changes deploy behaviour for required vars) |
| P4 | Part 3 steps 1-3: accessor layer + shadow read | low (read only) |
| P5 | Part 3 step 4: per-secret cutover | **high**, user-gated |

Each phase is its own PR; P0 is largely human/operational.

## Decisions needed

1. **Scope of migration (part 3):** agree that Coolify token, SSH keys,
   `infisical.json` and `mcp_token.json` stay as files (break-glass), and
   only Cloudflare and app-level credentials move?
2. **Auto-reuse folders:** `/apps/<app-name>` then `/shared`, as above, or a
   different convention?
3. **Untrusted repos:** is "owner reviews the analysis report" sufficient,
   or should `/shared` reuse need an explicit allowlist?
4. **Outage behaviour:** fail loudly (proposed) or fall back to raw
   `env_overrides` automatically when Infisical is unreachable?
5. **P0:** who owns backup/escrow of Infisical's `ENCRYPTION_KEY` and
   database, and is a restore drill acceptable before P3?
6. **Order:** P1 and P2 are safe to start now; hold P3 until P0 is done?
